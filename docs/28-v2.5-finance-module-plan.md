## 1. 需求原文拆解

| # | 原文 | 我的理解（口径见 §3.4） | 需业务方确认 |
|---|---|---|---|
| ① | 增加财务管理模块：付款单 | 我方付给**供应商**的付款台账（可核销到采购单） | 是否要审核、能否超额（§6 Q2/Q4） |

## 3. 设计草案

### 3.1 数据模型

**三张单据表**（各自独立，不合并成 `fund_orders + direction`）：与既有"一类单据一张表"一致，
权限点/编号/打印模板/前端配置天然分开，避免 `supplier_name` 与 `customer_name` 挤同一列导致语义模糊。

| 表 | 说明 | 关键字段（`DocMixin` 之外的） |
|---|---|---|
| `payment_orders` | 付款单 | `supplier_id/name`、`settle_type`（银行转账/现金/承兑）、`pay_account`（我方账户，自由文本）、`currency`、`total_amount` |
| `receipt_orders` | 收款单 | `customer_id/name`、`settle_type`、`recv_account`、`currency`、`total_amount` |
| `invoices` | 发票（进项/销项同表，`direction` 区分） | `direction`(in/out)、`invoice_code`、`invoice_no`、`invoice_type`（专票/普票/电子）、`tax_rate`、`amount`(不含税)、`tax_amount`、`total_amount`、`party_id/name`、`auth_status`（待认证/已认证，见 §6 Q3） |

**两张核销子表**（本次的核心）：

| 表 | 说明 | 字段 |
|---|---|---|
| `payment_allocations` | 付款单 → 采购单（或入库单） | `payment_id`、`target_type`(purchase_order/stock_in)、`target_id`、`target_no`、`amount` |
| `receipt_allocations` | 收款单 → 销售订单（或出库单） | 同上 |
| `invoice_allocations` | 发票 → 采购单/销售订单 | `invoice_id`、`target_type`、`target_id`、`target_no`、`amount`、`tax_amount` |

> **为什么 M1 就建核销表，而不是"付款单表头直接挂一个采购单"**：
> 表头单值方案实现最快，但一旦业务要求"一张付款单核销多张采购单 / 预付冲抵多单"，
> 就要做数据迁移与口径重算。先把核销表建好、M1 **界面只允许选一张单据**（多选后续放开），
> 数据结构不返工 —— 这是本项目在 V2.1（下推链）上已经吃过一次亏的地方。
> 若业务方明确"永远一对一"，可直接选 §6 Q1 的方案 C 简化。

**回写字段**（列表/导出零 join，与 `received_qty` 同构）：

| 表 | 新增字段 | 由谁回写（审核时 +，红冲时 −） |
|---|---|---|
| `purchase_orders` | `paid_amount`、`invoiced_amount` | 付款单、进项发票的核销金额 |
| `sales_orders` | `received_amount`、`invoiced_amount` | 收款单、销项发票的核销金额 |

### 3.2 状态机与记账口径

- **审核 = 记账**，反审核/作废 = **红冲**（与入库/出库过账同一个模式，`approve_handler` / `unapprove_handler`）。
- 草稿 / 已提交**不计入**进度（与"收货进度只认已过账入库单"一致，避免"填了就算"的虚假进度）。
- 已被下游引用时（例：采购单已有未作废的付款单）**禁止反审核/作废**，提示先处理下游 ——
  复用 `push_service.assert_no_downstream` 的同款校验与文案风格（AC-V2-24 口径）。
- 超额（付超/收超/开票超单）默认**允许登记但标红 + 列表可筛**，硬拦截会把"先付款后补单"的真实业务挡在门外（§6 Q4）。

### 3.3 进度列口径（本次最容易返工的地方）

| 列 | 分子 | 分母 | 数据来源 | 边界 |
|---|---|---|---|---|
| 收货进度（采购单） | Σ行项 `received_qty` | Σ行项 `qty` | **已有**：入库单过账回写 | 数量口径，未过账入库单不计 |
| 付款进度（采购单） | `paid_amount`（已审核未作废付款单的核销额） | `total_amount` | 新增 | 预付款若未核销到单据，**不计入**（单独在付款单列表可见） |
| 收票进度（采购单） | `invoiced_amount`（进项发票核销额） | `total_amount` | 新增 | 口径待定：含税（价税合计）还是不含税（§6 Q4） |
| 发货进度（销售订单） | Σ行项 `shipped_qty` | Σ行项 `qty` | **已有**：出库单过账回写 | 同上 |
| 收款进度（销售订单） | `received_amount` | `total_amount` | 新增 | 预收款同上 |
| 开票进度（销售订单） | `invoiced_amount` | `total_amount` | 新增 | 同上 |

展示规则（建议）：
- `0%` 灰、`0% < p < 100%` 蓝、`p = 100%` 绿、`p > 100%` 红（并显示真实百分比如 `120%`）；
- 分母为 0（金额/数量为 0 的单据）显示 `—`，不显示 `0%` 或 `∞`；
- 保留 1 位小数（`Math.round(p * 10) / 10`），避免 `66.66666%` 这种噪声；
- 作废/驳回单据的分子已由红冲回退，列上仍按剩余值显示。

### 3.4 「更多」快速发起（交互）

现在 `DocListPage.vue` 的「更多」下拉只有 打印 / 反审核 / 作废（第 701-713 行）。新增：

| 列表 | 「更多」新增项 | 跳转与预填 |
|---|---|---|
| 采购单 | 发起付款单 / 登记进项发票 | 跳付款单/发票新建页，带 `?source_type=purchase_order&source_id=<id>`；预填供应商、签约公司、来源单号、金额 = **未付/未收票金额** |
| 销售订单 | 发起收款单 / 登记销项发票 | 同理，预填客户 |

- 权限点独立（`finance.payment.create` …），无权限**不渲染**该项（前端体验 + 后端强制校验，AC-V2-41 不变）。
- 只对 `approved` / `completed` 且**未作废**的单据显示（与"下推"按钮的显隐口径一致）。
- 预填是"默认值"而非锁定：财务可改金额（部分付款）与结算方式；来源单号在单据上留快照（`source_doc_*`），
  与既有下推链的 `source_doc_type/id/no` 复用同一组字段。

## 5. 验收场景草案（确认口径后转正式 AC）

| 编号 | 场景 | 期望 |
|---|---|---|
| AC-FIN-01 | 采购单已审核，发起付款单并审核 | 采购单 `paid_amount` 增加、付款进度列同步变化 |

| AC-FIN-06 | 采购列表查看三列进度 | 百分比与颜色符合口径；导出的三列与列表一致 |
| AC-FIN-07 | 「更多 → 发起付款单」 | 跳转新建页并预填供应商/签约公司/金额；保存后来源单号留快照 |
| AC-FIN-08 | 无 `finance.payment.create` 权限的账号 | 「更多」里**不显示**该按钮，直接调接口返回 403 |

| AC-FIN-10 | 超额付款 / 超开票 | 允许登记但列表标红可按"超额"筛出（若选硬拦截口径则 422，见 Q4） |

## 6. 待确认问题（请业务方逐条定口径）

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| Q1 | 付款/收款与采购单/销售订单的核销粒度 | A 一付款单对一单据（表头单值）；B 核销明细表、M1 就支持多单；C 不做核销、只登记供应商总额 | **B**（M1 就建表、界面先一对一）——否则进度列做不出来，且后续要迁移 |
| Q2 | 付款单/收款单是否要审核 | A 提交 → 财务复核（两步）；B 录入即记账（一步）；C 仅登记不参与进度 | **A**（"钱"的口径建议留痕；若嫌慢可给财务保留一键审核） |
| Q3 | 发票管理的边界 | A 仅登记（号/金额/税额/关联单/附件）；B A + 认证/抵扣状态流转；C B + 红冲发票 | **B**（认证状态很有用，抵扣与税务申报不做） |
| Q4 | 进度金额口径与超额 | 含税（价税合计）还是不含税；超额允许还是拦截 | **含税** + **允许但标红**（先付后补单是真实业务） |
| Q5 | 谁能发起/审核 | 财务独占；还是采购员/销售员可发起、财务审核 | **业务员可发起、财务审核**（贴合"谁经手谁发起"） |
| Q6 | 合同「累计已付」是否改为自动回写 | 是 / 否（继续手工） | **是**（付款单落地后手工维护必然对不上） |
| Q7 | 本次迭代版本号 | V2.5（飞书=V2.4） / V2.4（按 `2.4prompt` 字面） / V2.6 | **V2.5**，飞书接入记作 V2.4 |
| Q8 | 里程碑取舍 | 先 M1+M2 / 只要进度列（先不做财务单据） | 先 **M1+M2**；若只做进度列，付款/收票/开票三列**没有数据源**，等于做不出来 |

## 7. 范围边界（本次明确不做）

| 项 | 原因 |
|---|---|
| 会计凭证 / 总账 / 科目体系 / 试算平衡 | `docs/11` §14.5 仍不做；引入凭证意味着要做借贷记账规则与期间结账，是另一个量级 |
| 税务申报、发票验真/开票接口对接（百望/航信） | 需外部系统与资质；本系统只登记票面信息 |
| 银行流水导入与自动对账 | 依赖银企直连或网银导出格式，先手工登记 |

## 10. G1 口径冻结结论（✅ 已定稿）

需求方逐条确认如下（问法见 §6，均为**推荐口径被采纳**）：

| # | 议题 | **冻结口径** | 对设计的影响 |
|---|---|---|---|
| Q1 | 核销粒度 | **建核销明细表，M1 界面先支持"一付款单核一张单"**，结构上支持多单（M3 放开界面） | 新增 3 张核销表（§3.1）；不返工、不迁移 |
| Q2 | 付款/收款审核流 | **草稿 → 提交 → 财务审核（记账）；反审核/作废红冲** | 记账点 = `approve`；复用 `posted` + `approve_handler` |
| Q3 | 发票边界 | **登记票面信息 + 认证状态（待认证 / 已认证）**；不做验真接口与税务申报 | 发票为简化状态机 `draft/confirmed/voided` + `auth_status` |
| Q4 | 进度金额口径 | **含税（价税合计）**；收货/发货为数量口径 | 分子分母均为 `total_amount` 一系；AC-V2.5-11 明确"用不含税金额不得显示 50%" |
| Q5 | 超额处理 | **允许登记，列表标红并可筛**（不硬拦截） | 不做上限校验；列表加"超额"筛选项 |
| Q6 | 角色分工 | **业务员发起、财务审核**（采购员→付款/进项票；销售员→收款/销项票） | 权限点按"发起"与"审核"分离；`finance` 角色独占 `approve` |
| Q7 | 本轮范围 | **M1 + M2**（财务单据内核 + 进度列与快速发起） | 任务拆解见 `docs/31` §2 |
| Q8 | 迭代命名 | **V2.5**（飞书接入 = V2.4） | 文档编号 28~32、提交前缀 `[V2.5]` |

**唯一未决项**：合同「累计已付 / 已收」是否由付款/收款单自动回写（原 §6 Q6）——
建议**做**（否则手工维护必然与单据对不上），定为 BR-V2.5-12，M2 开工前确认即可，不阻塞 M1。
