## 2. 数据模型增量

### 2.1 `ContractItem` 绑定物料（N4）

`app/models.py::ContractItem`（现位于 `:177`，字段：`item_type/name/spec/qty/unit_price/total/remark`）新增：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `product_id` | `Integer` FK→`products.id` | **nullable=True**，index | 绑定的系统物料档案 |
| `product_code` | `String(32)` | nullable | 物料编码**快照** |
| `product_name` | `String(128)` | nullable | 物料名称**快照** |

> **为何 DB 层可空、应用层必填**：SQLite `ALTER TABLE ADD COLUMN` 对既有表加 `NOT NULL` 需要默认值或重建表；且合同模块的导入/历史通道（`routers/contracts.py`）不适合硬约束。故**约束落在应用层**：新建、编辑、导入三处强制校验（`product_id` 必填）。
> **为何加名称/编码快照**：沿用 `DocItemMixin`（`models_doc.py:100-117`）的既有惯例——主数据改名不得影响历史单据/合同展示。
> **`name`/`spec` 保留可编辑**：绑定物料时自动带出物料名称/规格作为默认值，用户仍可覆盖，避免破坏合同既有文本语义与 Excel 导入历史格式。

### 2.3 调拨单据模型（N13）

新增 `app/models_doc.py`（与既有单据同文件，保持域内聚）：

```python
class StockTransfer(Base, DocMixin):
    __tablename__ = "stock_transfers"
    doc_type = "stock_transfer"
    direction = 0                      # 非入非出：不入 direction 驱动逻辑
    label = "调拨单"

    from_warehouse_id:   Mapped[int] = mapped_column(ForeignKey("warehouses.id"), nullable=False, index=True)
    from_warehouse_name: Mapped[str] = mapped_column(String(64), nullable=False, default="")   # 快照
    to_warehouse_id:     Mapped[int] = mapped_column(ForeignKey("warehouses.id"), nullable=False, index=True)
    to_warehouse_name:   Mapped[str] = mapped_column(String(64), nullable=False, default="")   # 快照

    items: Mapped[list["StockTransferItem"]] = relationship(
        back_populates="doc", cascade="all, delete-orphan",
        order_by="StockTransferItem.seq", lazy="selectin")


class StockTransferItem(Base, DocItemMixin):
    __tablename__ = "stock_transfer_items"
    doc_id: Mapped[int] = mapped_column(
        ForeignKey("stock_transfers.id", ondelete="CASCADE"), index=True)
    doc: Mapped[StockTransfer] = relationship(back_populates="items")
```

**设计要点**：
- 行项复用 `DocItemMixin`（物料快照、数量、单位精度校验全部免费获得）；`warehouse_id` 列**不使用**（仓库由表头两仓决定），保持"不使用"而非删除，以维持 7 类单据的同构性；
- `unit_price`/`amount` 固定为 0（调拨不产生金额，BR-V2.1-08）；
- **两仓不同**校验：应用层（`doc_service` 保存/提交时），并建议加 `CheckConstraint("from_warehouse_id <> to_warehouse_id")`；
- **同组织**校验：两仓的 `org_id` 一致（Q4 冻结结论），跨组织直接拒绝。

## 3. N3 缺陷根因分析与修复设计 ★

### 3.1 现象

采购申请单（及所有使用通用行项表的单据）行项表格的**合计行金额列**显示 `[object Object]`，而行内金额列显示正常。

### 3.2 根因（已确证，非推测）

`web/src/components/doc/DocItemsTable.vue`：

| 位置 | 代码 | 问题 |
|---|---|---|
| `:93` | `const totalAmount = computed(() => props.items.reduce(...))` | 产生 **`ComputedRef<number>` 对象**，不是数字 |
| `:173` | `if (i === 6) return fmtMoney(totalAmount)` | **在 `<script>` 的函数体内读取 ref 未加 `.value`** → 传入的是 ref 对象本身 |
| `:80-84` | `const n = Number(v)` → `Number.isNaN(n) ? String(v) : ...` | `Number(ref对象)` = `NaN` → 走 **`String(v)`** 分支 → `String(ComputedRef)` = `"[object Object]"` |

**完整链路**：`totalAmount`(ref) → `fmtMoney(ref)` → `Number(ref)`=`NaN` → `Number.isNaN(NaN)`为真 → `String(ref)` → `"[object Object]"`。

**为何只在合计行出错**：行内金额走 `fmtMoney(amountOf(row))`（`:236`），`amountOf` 返回真正的 `number`（`:90`），故正常。

**为何模板里同样的写法不出错**：Vue 模板对 `setup` 暴露的 ref 会**自动解包**（如 `ContractsView.vue:905` 的 `{{ fmtMoney(itemsTotal) }}` 是安全的）；但 `summaryMethod` 是 **script 内的普通函数**，不存在解包，必须显式 `.value`。

### 3.3 为何既有质量门禁没有拦住

| 门禁 | 为何失效 |
|---|---|
| `npm run build` | ⚠️ **该项目 `build` 脚本是纯 `vite build`，不含任何类型检查**（`web/package.json` 的 devDependencies 无 `vue-tsc`，也没有 `tsc --noEmit`）→ **类型层根本没有把关环节**。即便补上类型检查，本缺陷仍可能漏过：`fmtMoney(v: unknown)` 接受任意入参，而 `"[object Object]"` **确实是 string**，满足返回类型 `string[]` |
| 后端 `pytest` | 缺陷纯在前端渲染层，后端 `amount` 计算正确 |
| API 级冒烟 `smoke_m*` | 只断言接口 JSON，**不读前端渲染结果** |
| 人工 UI 验收 | `20-v2-acceptance-summary.md` §5 已登记"浏览器自动化组件不可用，UI 目视未自动化"→ 漏网 |

> **结论**：这不是"某个门禁的偶然失效"，而是**前端质量门禁的整体缺口**——没有类型检查、没有组件级测试、API 冒烟又只看接口。V2.1 的补强落在两处：① 用**项目已装的 Playwright e2e** 覆盖渲染结果（见 §3.4 L4）；② 在 `03` §13.2 的 M1 DoD 中固化"合计行金额"断言。
> **附带建议**：增加 `vue-tsc --noEmit` 作为 `build` 前置——这是本次缺陷暴露出的**独立于 N3 的工程改进项**，可拦截同类 `ref` 误用。

### 3.4 修复设计（三层）

**L1 — 正确性修复（必须）**

```ts
if (i === amountColIndex) return fmtMoney(totalAmount.value)   // ← 补 .value
```

**L2 — 消除同类隐患（加固）**

将 `fmtMoney` 的"非数字回退"从 `String(v)` 改为**安全数值化 + 显式兜底**，使任何误传对象不再伪装成合法输出：

```ts
function fmtMoney(v: unknown): string {
  if (v === null || v === undefined || v === '') return '0.00'
  const n = typeof v === 'number' ? v : Number(v)
  if (!Number.isFinite(n)) {
    if (import.meta.env.DEV) console.warn('[fmtMoney] 非数值入参：', v)   // 开发期暴露同类错误
    return '0.00'
  }
  return n.toLocaleString('zh-CN', { minimumFractionDigits: 2, maximumFractionDigits: 2 })
}
```

**L3 — 消除脆弱定位（加固）**

合计行的目标列不得依赖**硬编码索引** `i === 6`（`DocItemsTable.vue:170-176`）。当前列序下 `6` 恰为金额列，但 `showWarehouse` / `extraCols` / `readonly` 任一组合变化都会让该假设失效（`12` 已把该表列为 7 类单据共用组件）：

```ts
function summaryMethod({ columns }: { columns: { property?: string }[] }): string[] {
  const amountIdx = columns.findIndex((c) => c.property === 'amount')
  return columns.map((_c, i) => {
    if (i === 0) return '合计'
    if (i === amountIdx) return fmtMoney(totalAmount.value)
    return ''
  })
}
```

并在模板对应列上声明标识：

```html
<el-table-column label="金额" prop="amount" width="120" align="right">
```

**L4 — 测试补强（防复发）**

| 层级 | 措施 |
|---|---|
| **端到端（已落地，零新依赖）** | 项目**已装 Playwright**（`web/package.json` 的 `test:e2e`，用例在 `web/tests/e2e/*.spec.ts`）。已在 `06-purchase.spec.ts` 新增用例：录入数量 3 × 单价 5 → 断言合计行**含** `合计` 与 `15.00`、**不含** `[object Object]`（该方法首行即为最省事的同类回归防线） |
| 组件级（可选，需新依赖） | 若要直接覆盖 `fmtMoney` 的"误传对象"分支，需引入 vitest（**当前未安装**）。**非必需**——L2 已从实现上消除了对象回退路径 |
| 类型检查（建议独立立项） | `vue-tsc --noEmit` 接入 `build` 前置。当前项目**完全没有**前端类型检查门禁（见 §3.3），这是比 N3 本身更值得补的缺口 |

### 3.7 连带发现：`dicts.py::_load_list` 类型不匹配（⚠️ 会阻断 N16）

**现象**：干净库（KV 中无 `item_types`）上请求 `/api/meta` 返回 **500**。

**根因**：`app/dicts.py:46`（修复前）

```python
return [dict(x) for x in default]      # ⚠️ default 的元素类型并不固定
```

`_load_list` 被三类字典共用，而它们的默认值类型不同：

| 字典 | 默认值类型 | `dict(x)` 是否成立 |
|---|---|---|
| `item_types`（`DEFAULT_ITEM_TYPES`） | **`list[str]`** | ❌ `dict('采购')` → `ValueError: dictionary update sequence element #0 has length 1; 2 is required` |
| `contract_types` / `subjects` | `list[dict]` | ✅ 正常 |

**为何此前从未暴露**：真实演示库的 KV 中早已存在 `item_types`（历史 seed 写入），代码永远走不到默认值分支；而 `init_db` 主流程**只 seed tags**（`init_db.py::seed_dicts`），并不 seed 其余字典。

**为何必须在 V2.1 修**：**N16 采用清库重建**（`init_db` + `seed_demo_v2.py`），重建后若 KV 无 `item_types` → `/api/meta` 500 → 前端合同/单据页面大范围不可用，**直接阻断 M1.5**。

**修复（已落地）**：`_load_list` 改为对默认值做**整体深拷贝**，不再对元素做结构化转换：

```python
from copy import deepcopy
...
    if row is None:
        return deepcopy(default)
```

**验证**：修复前干净库 `243 passed, 1 failed`；修复后 **`244 passed`** —— 即**干净库首次达到 `20` 声明的基线**。

## 6. 调拨过账设计（N13，核心）★

### 6.1 为何不能直接复用 `post_stock_doc`

`post_stock_doc`（`posting_service.py:54-109`）的设计前提是**单据单一方向**：

```python
sign = (1 if doc.direction > 0 else -1) * (-1 if reverse else 1)   # :61
delta = sign * (item.qty or ZERO)                                  # :68
```

一张调拨单需要**同时**产生"调出仓减"与"调入仓加"两个相反方向的变动，`direction` 单值模型无法表达。故**新增 `post_transfer()`**，不改动既有函数（避免影响 8 类单据的过账回归）。

### 6.2 `post_transfer()` 设计

```python
def post_transfer(db: Session, doc, *, user, reverse: bool = False) -> int:
    """调拨过账：调出仓减、调入仓加（同事务）；reverse=True 为红冲。返回流水条数。"""
    params = get_sys_params(db)
    if not reverse and doc.posted:
        return 0                                     # 幂等（AC-V2.1-17）

    # ── 阶段一：全量校验（先算后写，避免"写一半失败"）──
    plans = []
    for item in doc.items:
        out = _get_stock(db, item.product_id, doc.from_warehouse_id)
        if (not reverse and not params.get("allow_negative_stock", False)
                and (out.qty or ZERO) < (item.qty or ZERO)):
            raise BusinessError(                     # AC-V2.1-16
                f"{doc.from_warehouse_name} 物料「{item.product_name}」库存不足"
                f"（可用 {out.qty}，需要 {item.qty}）")
        inn = _get_stock(db, item.product_id, doc.to_warehouse_id)
        plans.append((item, out, inn))

    # ── 阶段二：统一写入（任一异常由路由层事务整体回滚）──
    written = 0
    for item, out, inn in plans:
        qty = item.qty or ZERO
        # 调出仓
        out.qty = (out.qty or ZERO) - qty if not reverse else (out.qty or ZERO) + qty
        _write_ledger(db, doc, item, out, biz_type="调拨出库",
                      qty_change=(-qty if not reverse else qty), user=user, reverse=reverse)
        # 调入仓
        inn.qty = (inn.qty or ZERO) + qty if not reverse else (inn.qty or ZERO) - qty
        _write_ledger(db, doc, item, inn, biz_type="调拨入库",
                      qty_change=(qty if not reverse else -qty), user=user, reverse=reverse)
        written += 2

    doc.posted = not reverse
    audit_service.log(db, user, module="stock",
                      action="unapprove" if reverse else "approve",
                      object_type=doc.doc_type, object_id=doc.id, object_no=doc.doc_no,
                      detail=("反审核红冲" if reverse else "审核过账") + f"（{written} 条流水）")
    return written
```

**红冲记录**：`biz_type` 前缀 `红冲-`（沿用 `posting_service.py:84` 的既有惯例）→ `红冲-调拨出库` / `红冲-调拨入库`。

### 6.3 审核/反审核封装（与既有单据同构）

```python
def approve_transfer(db, doc, user) -> int:
    if doc.posted and doc.status == "approved":
        return 0                                     # 幂等短路（同 approve_stock_doc:117）
    doc_service.approve(db, doc, user)               # 状态流转 + 变更历史
    return post_transfer(db, doc, user=user)

def unapprove_transfer(db, doc, reason, user) -> int:
    doc_service.unapprove(db, doc, reason, user)
    return post_transfer(db, doc, user=user, reverse=True)
```

### 6.4 过账时序（AC-V2.1-15）

```
审核动作
  │
  ├─ ① doc_service.approve：status 待审核 → 已审核，写变更历史/操作日志
  ├─ ② 幂等短路：doc.posted 已为真则直接返回 0
  ├─ ③ 阶段一 校验：行项非空 → 调出仓可用量 ≥ 调出量（不足则 BusinessError）
  └─ ④ 阶段二 写入（同一 DB 事务）
        ├─ 调出仓 stock.qty −= qty ；ledger(调拨出库, −qty, qty_after)
        ├─ 调入仓 stock.qty += qty ；ledger(调拨入库, +qty, qty_after)
        └─ doc.posted = True
  │
  ├─ 成功 → 路由层 commit
  └─ 失败 → 路由层 rollback（status/stock/ledger 全部还原，AC-V2.1-16）
```

**不变式**：过账后仍须满足 `stocks.qty == SUM(stock_ledger.qty_change)`（AC-V2-26），`POST /api/stock/recalc` 可校验——调拨只是**两条等量反向流水**，天然保持该不变式。

### 6.5 幂等与并发

| 场景 | 机制 |
|---|---|
| 重复审核（同进程/重复点击） | `doc.posted` 短路（阶段②），与 `approve_stock_doc:117` 同款 |
| 并发审核 | SQLite 单写者 + 路由层事务；`doc.posted` 在事务内读写，第二次进入时已为真 |
| 反审核后重审 | `doc.posted=False` → 可再次过账，流水**追加**（不修改历史），符合"流水只增不改"（`models_stock.py:4`） |

> **不引入流水唯一索引的原因**：既有 8 类单据均无该约束，单独为调拨加会导致机制不一致；幂等由 `posted` 标志与事务保证，与现状对齐。

## 7. 货品总额度计算设计（N11）★

### 7.1 口径落地（BR-V2.1-09）

「货品总额度」= 该 `(物料 × 仓库)` 的**所有批次入库金额合计**：

```sql
SELECT product_id, warehouse_id,
       SUM(qty_change * COALESCE(unit_price, 0)) AS inbound_amount
FROM stock_ledger
WHERE biz_type LIKE '%入库%'            -- 采购/退货/盘盈/其他 入库，及其"红冲-"记录
  AND biz_type NOT LIKE '%调拨入库%'     -- 排除调拨入库（含"红冲-调拨入库"）
GROUP BY product_id, warehouse_id
```

**逐条对应口径**：

| 口径要求 | 实现方式 |
|---|---|
| 按 物料×仓库 聚合 | `GROUP BY product_id, warehouse_id`（不跨仓库合并） |
| 只统计入库方向 | `biz_type LIKE '%入库%'`（`BIZ_TYPES` 中入库类均以"入库"结尾） |
| 负向冲减 | 红冲记录 `biz_type="红冲-采购入库"` 命中 `%入库%`，其 `qty_change` 为**负**，求和时自动冲减 |
| 排除调拨入库 | `NOT LIKE '%调拨入库%'`（同时排除其红冲记录） |
| 缺失单价按 0 | `COALESCE(unit_price, 0)` |

> ⚠️ **实现陷阱**：**不能**用 `WHERE qty_change > 0` 作为"入库方向"的判据——红冲入库的 `qty_change` 为负，会被漏掉而**无法冲减**，导致额度虚高。必须以 `biz_type` 判定方向。

### 7.2 查询集成

库存明细接口（`/api/stock/balances`）以**子查询 LEFT JOIN** 方式集成，避免逐行 N+1：

```python
sub = (db.query(StockLedger.product_id, StockLedger.warehouse_id,
                func.sum(StockLedger.qty_change * func.coalesce(StockLedger.unit_price, 0))
                  .label("inbound_amount"))
         .filter(StockLedger.biz_type.like("%入库%"),
                 StockLedger.biz_type.notlike("%调拨入库%"))
         .group_by(StockLedger.product_id, StockLedger.warehouse_id).subquery())
rows = (db.query(Stock, sub.c.inbound_amount)
          .outerjoin(sub, and_(sub.c.product_id == Stock.product_id,
                               sub.c.warehouse_id == Stock.warehouse_id))
          ...)
```

**索引**：`stock_ledger(product_id, warehouse_id, biz_type)`（见 §2.6 第 4 条）。

**筛选**：`qty_min` / `qty_max` 直接过滤 `Stock.qty`；`product_type_id` 走 §5.3 的 path 前缀匹配。

### 9.2 重建流程（不可逆，须前置确认）

```
① 业务方书面确认"库内数据可弃"           ← 强制门禁（19-go-live-checklist）
② 停服
③ 备份现有库：app/data/ctms.db → backup/ctms-v2.0-YYYYMMDD.db
④ 移走旧库：ctms.db → ctms.db.bak
⑤ python -m app.init_db                 # 建表 + 种子 + 增量迁移
⑥ python app/tools/seed_demo_v2.py --no-force-change
      └─ 扩展后：演示合同自带行项且每行绑定物料
⑦ 验证：AC-V2.1-21 + 重跑 smoke_m1（确认权限基线未漂移，R10）
```

### 9.3 脚本改造（`seed_demo_v2.py`）

在 `_ensure_contracts()`（`:192-254`）内，为每份演示合同创建 2~3 条 `ContractItem`：

```python
item = ContractItem(
    seq=i + 1, item_type=..., name=product.name, spec=product.spec,
    qty=Decimal("10"), unit_price=Decimal("100"), total=Decimal("1000.00"),
    product_id=product.id,                    # ★ V2.1：绑定物料
    product_code=product.code, product_name=product.name,
)
```

**依赖顺序**：物料必须先于合同行项创建（既有脚本已保证 `_get_or_create_product` 在 `_ensure_contracts` 之前调用）。

**数据覆盖要求**（支撑验收）：
- 至少 1 份**采购方向**合同含 ≥3 条已绑定物料的行项 → 支撑 AC-V2.1-02；
- 至少 1 份合同可被下推为采购单 → 支撑 AC-V2.1-10；
- 至少 1 个物料在演示仓库有 ≥2 次入库（不同单价）→ 支撑 AC-V2.1-11 的额度计算验证。

> **⚠️ 设计决策：V2.1 重建不使用 `init_db --demo`**。该路径会生成**无行项**的 V1.0 风格演示合同，与 N2 的能力冲突。演示数据统一由 `seed_demo_v2.py` 提供；若确需保留原型合同，需同步改造 `seed_demo` 补行项（建议不做，减少重复真相）。
