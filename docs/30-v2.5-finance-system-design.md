## 2. 数据模型增量

### 2.1 三张单据表（均继承 `DocMixin`）

```python
class PaymentOrder(Base, DocMixin):          # payment_orders
    doc_type = "payment";  direction = 0;  label = "付款单"
    supplier_id:   int  FK suppliers.id, nullable=False, index
    supplier_name: str(128) 快照
    settle_type:   str(24)    # 银行转账/现金/承兑/其他
    pay_account:   str(64)    # 我方付款账户（自由文本，不建账户档案）
    currency:      str(8)     # 默认 CNY
    total_amount:  Numeric(16,2)          # 付款金额（含税）

class ReceiptOrder(Base, DocMixin):          # receipt_orders
    doc_type = "receipt";  direction = 0;  label = "收款单"
    customer_id / customer_name / settle_type / recv_account / currency / total_amount

class Invoice(Base, DocMixin):               # invoices
    doc_type = "invoice";  label = "发票"
    invoice_direction: str(8) # in=进项 / out=销项（index）★列名不叫 direction，见下方说明
    invoice_code: str(32)     # 发票代码（可空：电子发票常无）
    invoice_no:   str(64)     # 发票号码（必填）
    invoice_type: str(16)     # 增值税专用发票/增值税普通发票/电子发票
    invoice_date: Date
    tax_rate:     Numeric(5,2)     # 13.00
    amount:       Numeric(16,2)    # 不含税金额
    tax_amount:   Numeric(16,2)    # 税额
    total_amount: Numeric(16,2)    # 价税合计（进度口径）
    party_id / party_name          # 进项=供应商，销项=客户
    auth_status:  str(16) = "pending"   # pending 待认证 / verified 已认证
    __table_args__ = (UniqueConstraint("invoice_direction", "invoice_no", name="uq_invoice_dir_no"),)
```

> ⚠️ **命名避让：发票的"进项/销项"列必须叫 `invoice_direction`，不能叫 `direction`。**
> `models_doc` 里 `direction` 是一个**整数类属性约定**（入库 `1` / 出库 `-1` / 其余 `0`），
> `posting_service.post_stock_doc` 第 61 行直接读 `doc.direction` 决定过账正负号。
> 若发票用同名列且类型为字符串，一旦有通用代码（打印、导出、看板、未来的过账扩展）按约定读 `direction`，
> 就会拿到 `"in"/"out"` 而不是 ±1，属于"静默错误的过账方向"——最难排查的一类缺陷。
> 付款单/收款单同样只声明 `direction = 0`（不参与任何过账），不借用该属性表达业务方向。
> API 与界面上的查询参数仍可使用 `direction`（对外语义），只在**列名**上避让。

- `Invoice` 的 `status` 用**简化态**：`draft / confirmed / voided`（不用 submitted/approved/completed）；
  **不复用** `register_doc_routes` 的完整状态机（那套是"提交→审核→完成"的业务流），
  发票走独立的 `confirm`（确认入账）与 `voided` 两个动作 —— 这样部门/主管审批不会误挂到发票上。
- **不要动全局 `DOC_STATUS`**：`doc_routes` 第 140 行把 `DOC_STATUS` 直接当所有工厂单据的状态下拉，
  往里加 `confirmed` 会让采购/销售/库存列表多出一个永远筛不到的「已确认」。
  发票改用独立映射 `INVOICE_STATUS = {"draft": "草稿", "confirmed": "已确认", "voided": "已作废"}`
  与独立 serializer（`doc_service` 的 `_ensure_status` 文案同样传发票自己的字典）。
- 发票仍复用 `DocMixin`（编号/日期/主体/审计/附件/变更历史全部免费）。

### 2.2 三张核销表（多态目标）

```python
class PaymentAllocation(Base):               # payment_allocations
    id; payment_id  FK payment_orders.id ON DELETE CASCADE, index
    target_type: str(24)     # purchase_order / stock_in
    target_id:   int         # index（与 target_type 组合检索）
    target_no:   str(32)     # 单号快照（目标单据被删/改名仍可追溯）
    amount:      Numeric(16,2)
    remark:      Text

class ReceiptAllocation(Base):               # receipt_allocations（target_type: sales_order / stock_out）
class InvoiceAllocation(Base):               # invoice_allocations（target_type: purchase_order / sales_order）
    # 额外 tax_amount：发票含税分摊中的税额（报表口径用，进度不参与）
```

**为什么目标用多态 `(target_type, target_id)` 而不是外键**：付款可能核销到**入库单**（先收货后补票的场景）、
发票可能核销到采购单或销售订单 —— 单一外键表达不了；多态 + 应用层校验是本项目的既有取舍
（`DocMixin.source_doc_type/source_doc_id`、`Notification` 的收件人就是同一风格）。
代价是数据库层没有外键保护，因此**所有写入都只经过 `finance_service`**（见 §3），并在重算接口里兜底。

## 3. 核销与记账设计（核心）

### 3.1 记账点与幂等标记：复用 `posted`

`DocMixin` 已有 `posted: bool`（入库/出库用它表示"库存已过账"）。财务单据用它表示**"金额已记账"**：

- 审核（`approve`）→ `posted=False → True`（**原子条件更新**，抢占成功才记账）；
- 反审核（`unapprove`）→ `posted=True → False`（原子回退），并红冲；
- 作废只对 `draft/submitted` 生效（`doc_service._ensure_status` 已如此约束），**未记账，无需红冲**；
- 因此"重复审核/重复反审核"天然幂等（第二次条件更新影响 0 行 → 直接拒绝或幂等返回，BR-V2.5-10）。

> 先例教训：`docs/27` §10.2 记录过"原子抢占后用 ORM 陈旧对象写回、覆盖抢占结果"的真实缺陷。
> 财务这里的原子更新沿用同一处理：`query.update(synchronize_session=False)` 后 **`db.expire_all()`**，
> 再读核销明细与目标单据。

### 3.2 `finance_service` 公开函数（唯一写入口）

| 函数 | 职责 |
|---|---|
| `parse_allocations(db, doc, rows)` | 校验并整体替换核销明细：目标单据存在、未作废、状态为 `approved/completed`、金额 > 0、单位匹配（付款→采购线、收款→销售线） |
| `approve_fund_doc(db, doc, user)` | 付款单/收款单审核：原子置 `posted` → 回写目标单据 `paid_amount`/`received_amount` → 审计 |
| `unapprove_fund_doc(db, doc, user)` | 反审核：原子清 `posted` → **精确回退**回写值（`max(0, 旧值-本次)`）→ 审计 |
| `confirm_invoice(db, inv, user)` | 发票确认：原子置 `posted` → 回写 `invoiced_amount`（进项→采购单，销项→销售订单） |
| `void_invoice(db, inv, user)` | 发票作废：若已 `posted` 则先红冲再作废（发票没有"反审核"动作，合并处理） |
| `verify_invoice(db, inv, auth_status, user)` | 认证状态流转（不影响进度） |
| `assert_no_finance_downstream(db, doc)` | 目标单据反审核前校验：存在**已记账**的下游核销则拒绝（BR-V2.5-04） |
| `progress_of(db, doc) -> dict` | 单张单据的六条进度（分子/分母/百分比），列表与详情共用 |
| `recalc_progress(db, kinds=None) -> dict` | 按核销表**重算**四个回写字段，返回修正条数与明细（运维兜底） |

### 3.3 记账事务的顺序（每个动作同一事务）

```
1) 权限（路由层 require_perm）
2) 校验：状态合法、posted 抢占成功、核销目标仍可记账（未作废、未反审核）
3) 原子更新 posted + expire_all()
4) 写/回退 目标单据回写字段（若目标单据已被删除则**跳过并记录告警**，不阻断 —— 但重算会暴露）
5) doc_service.log（变更历史）+ audit_service.log（操作日志）
6) 入队飞书通知（M2 可选，同事务 outbox，见 docs/27 §4.3 的硬约束）
7) commit
```

### 3.4 下游保护接在哪

`doc_service.unapprove()` 现在调用 `push_service.assert_no_downstream(db, doc)`（第 254 行）。
本次在**同一处**追加 `finance_service.assert_no_finance_downstream(db, doc)`：

```python
exists = (db.query(PaymentAllocation.id)
          .join(PaymentOrder, PaymentOrder.id == PaymentAllocation.payment_id)
          .filter(PaymentAllocation.target_type == doc.doc_type,
                  PaymentAllocation.target_id == doc.id,
                  PaymentOrder.status == "approved")     # 只看已记账的
          .first())
```
措辞沿用既有风格：「已存在付款单 PAY-xxxxxxx，请先反审核该付款单后再操作」。
**草稿/已提交的付款单不阻止上游作废**（尚未记账），但它在**审核时**会因为"目标单据已作废"被拒 —— 两条规则合起来才是完整的。

### 3.5 重算接口

`POST /api/finance/recalc`（`finance.payment.approve` 权限）：

1. 用 `SELECT target_type, target_id, SUM(amount) … GROUP BY` 聚合三张核销表（只算 `posted=True` 的单据）；
2. 与四列回写值比对，不一致则更新并记录差异；
3. 返回 `{checked, fixed, diffs:[{doc_no, field, old, new}]}`；
4. **不修改**任何核销明细与单据状态（只重建聚合值），可安全重复执行。

## 4. 进度计算与序列化

```python
# finance_service.progress_of(db, doc) -> dict
{
  "received":  {"num": 30, "den": 100, "pct": 30.0, "label": "收货进度"},   # 数量口径（采购单）
  "paid":      {"num": 3000.0, "den": 10000.0, "pct": 30.0},
  "invoiced":  {"num": 0.0, "den": 10000.0, "pct": 0.0},
}
```

- **只在采购单/销售订单**的 `fmt_doc` 里附加（`if doc.doc_type in ("purchase_order", "sales_order")`），
  其余单据不返回该字段（避免无意义的负载与前端分支）；
- `pct` 由**后端**算好（`round(num/den*100, 1)`），前端只渲染 —— 避免前后端两套算法漂移；
  `den == 0` 时 `pct = None`（前端显示 `—`）；
- 列表与导出**共用同一个函数**（`_build_query` 同一数据范围，AC-V2.5-16）；
- 收货/发货进度取行项 `received_qty`/`shipped_qty` 的求和（`doc.items` 已经 `lazy="selectin"`，列表页无额外查询）。

## 9. 风险与对策（设计层面）

| # | 风险 | 设计对策 |
|---|---|---|
| 1 | 回写与核销明细不一致 | 唯一写入口 + 原子 `posted` + 同事务 + `recalc` 兜底（§3.2、§3.5） |
| 2 | 目标单据被作废后仍被记账 | 审核时校验目标状态（§3.2 `parse_allocations`）；上游反审核时下游保护（§3.4）——双向闸门 |
| 3 | 多态目标无外键 | 写入只经服务层 + `target_no` 快照 + 重算暴露孤儿行 |

| 5 | 进度算法前后端不一致 | `pct` 由后端算（§4），前端只渲染 |
| 6 | 财务单据免行项导致表单壳误校验 | `DocFormPage.showItems=false` + `requireItems=false`（后端 `apply_items` 对 `rows=None` 本就直通） |
