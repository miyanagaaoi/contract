# V2.3 迭代记录（多公司维度 + PostgreSQL 迁移）

> 触发：业务方在 V2.2 之后提出的五条需求（仓库归属公司、单据签约公司、库存按公司筛选、
> 调拨出入单位、启动 PostgreSQL 并迁移数据）。
> 性质：`v2.0` / `v2.2` 之后的小版本迭代 —— **不动业务状态机与过账口径**，
> 新增「我方公司（主体码）」这一维度并落地到仓库 / 单据 / 库存 / 调拨，
> 同时把运行库从 SQLite 切到 PostgreSQL（含数据迁移与 Docker 发布编排）。
> 验证基线（详见 §8）：`pytest` 329 passed；前端 Playwright E2E 全量通过；
> 端到端冒烟 M1 15/15、M2 11/11、M3 11/11（**跑在 PostgreSQL 上**）；
> V2.3 专项冒烟 11/11。

## 2. 需求①：仓库「所属公司」与默认显示名

- **字段**：`warehouses.subject_code VARCHAR(8)`（可空，建索引）。取值经
  `dicts.require_subject_code` 风格校验（`master_service._subject_of`）：空的放行，
  非空必须**精确命中**系统设置里的主体码或其名称，否则 422
  「所属公司只能选择系统设置中的我方公司」。
- **显示口径唯一**：`master_service.warehouse_display(db, wh)` 是**唯一**的显示名实现，
  `ZC-主仓`。它同时被用于：
  - 仓库档案接口的 `display_name`（列表新增「所属公司」「显示名」两列）；
  - `/api/master/options/warehouse`（单据表头仓库、行级仓库、库存筛选下拉）；
  - **单据表头/行项的 `warehouse_name` 快照**（保存时落 `ZC-主仓`，历史快照不随后续改名变化）；
  - 库存明细与结存/流水导出的仓库列；看板与重算的仓库展示仍用纯仓库名（运维口径）。
- **存量兼容**：仓库未维护所属公司时显示名 = 纯仓库名，不会出现 `-主仓` 这种空前缀。
- 表单支持 `type: 'subjects'`（新增字段类型），下拉 label 为 `名称（主体码）`、
  value 存主体码，保证「只能选字典里的公司」。

## 3. 需求②：六类单据「签约公司」（必填）

- **字段**：`DocMixin` 增加 `subject_code` + `subject_name`（快照），八张单据表统一持有
  （盘点单/调拨单暂不使用该字段，接口层不对它们强制）。
- **必填校验**（`register_doc_routes(sign_subject=True)`，仅上述六类注册）：
  - 新建：缺少或取值为空 → 422「请选择签约公司」；取值不在字典 → 422
    「签约公司只能选择系统设置中的我方公司」；
  - 修改：显式传 `subject_code` 时同样校验，**空值视为非法**（必填字段不能清空）；
  - 下推：`push_service._inherit_subject` 从来源单据继承；来源单据无签约公司时**明确报错**
    「来源单据 XXX 未填写签约公司，请先在来源单据上补齐后再下推」，而不是生成空值单据
    （否则会绕过接口层校验，产生"看起来正常但无法对账"的数据）。
- **前端**：`DocFormPage` 新增 `show-subject` 开关（六个表单页传 true），表头渲染「签约公司」
  下拉（`clearable=false`），并有两处兜底，避免"默认值/异步竞态"把用户挡在保存之外：
  1. 新建时默认选中第一个我方公司，且该动作**抑制脏标记**——否则一进表单就被判为
     "未保存"，返回列表会被拦截（E2E `12-unsaved-guard` 实测复现）；
  2. 保存前 `await ensureSubjects()` 兜底——字典是异步拉取的，用户进入后立刻点保存时，
     默认值可能尚未落到表头（E2E `06-purchase` 实测：提示词从「请至少添加一行行项」
     变成「请选择签约公司」）。
     注意这里**不能**用 `markClean()` 清脏：若用户在字典返回前已录入内容，清脏会把真实的
     未保存修改一并抹掉。
- **可见性**：列表新增「签约公司」列与筛选项（`subject_code` 查询参数，列表与导出同口径）；
  详情抽屉、导出的「签约公司」（名称快照，缺快照时回退主体码）、打印模板
  （新增可配置表头字段「签约公司」，旧模板需在「打印模板」页勾选后才显示）。

## 4. 需求③：库存明细按公司筛选

- `/api/stock/balances` 与 `/api/stock/balances/export.xlsx` 新增 `subject_code` 参数，
  查询用 `Stock.warehouse.has(Warehouse.subject_code == code)` 过滤
  （用 EXISTS 而非再 join：结存查询已 join 了「货品总额度」子查询，避免 join 冲突）。
- 返回行新增 `warehouse_display_name` / `subject_code` / `subject_name`；
  页面新增「公司」筛选项与「公司」列，仓库列显示 `ZC-主仓`。
- 导出新增「公司」列、仓库列改为默认显示名，**导出条数与列表筛选一致**（AC-V2-40 不变）。

## 5. 需求④：调拨单「调出单位 / 调入单位」

- 表头新增四个快照字段：`from_subject_code|name`、`to_subject_code|name`。
- 取值来源：调出仓/调入仓的 `subject_code`（`_apply_transfer_fields` 在校验两仓不同后一并写入）；
  仓库未维护所属公司时为空，前端显示「—」。
- 前端表单新增两个**只读**输入框（随仓库选择即时显示公司名称）；列表详情抽屉同步展示。
- 说明：本版仍不校验"跨公司禁止调拨"（那属于业务策略），只把归属变化**显性化**出来。

## 6. 需求⑤：PostgreSQL 启动与数据迁移

### 6.1 实例与库

| 项 | 值 |
|---|---|
| 地址 | `192.168.31.27:5444`（PostgreSQL 18.6） |
| 库 | `ctms`（本次新建；原实例只有 `postgres` 库） |
| 连接串 | `postgresql+psycopg2://postgres:***@192.168.31.27:5444/ctms` |

后端通过既有 `CTMS_DB_URL` 环境变量切换，代码无需改动：

```bash
set CTMS_DB_URL=postgresql+psycopg2://postgres:good789good@192.168.31.27:5444/ctms
app\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

### 6.2 迁移工具（新增）

`app/tools/migrate_sqlite_to_pg.py`：

1. 用 ORM 元数据在目标库建表，并补齐 `db_migrate._ADD_COLUMNS/_ADD_INDEXES` 的增量列与索引
   （与 SQLite 侧同源，避免两套口径）；
2. 反射源 SQLite，按外键依赖顺序逐表拷贝（布尔/日期/数值由 SQLAlchemy 按目标方言转换）；
3. **重置自增序列**为 `max(id)`——SQLite 没有这个概念，漏做会导致后续插入主键冲突；
4. 迁移后逐表比对行数，不一致直接以非 0 退出码失败（避免"看起来成功"的静默故障）。
5. 支持 `--truncate`（清空目标库）与 `--dry-run` / `--verify-only`。

本次实测：首次迁移 **24 张表、5320 行**，重迁（`--truncate`，含 E2E 期间的增量数据）
**5431 行**，两次行数校验均通过。

`app/tools/backfill_subject_v23.py`：存量数据回填（只填空值、幂等）——
仓库所属公司、入库/出库单按**表头仓库所属公司**推断签约公司、其余单据用默认主体、
调拨单按两端仓库推断单位。本次回填：仓库 4、入库单 33、采购申请 166、采购单 32、销售订单 30。

### 6.3 迁移中发现并修复的兼容问题

1. **`contract_tag.auto` 的 `server_default=text("0")`**：SQLite 方言写法，在 PG 上建表报
   `column "auto" is of type boolean but default expression is of type integer`。
   改为 `server_default=false()`（按方言渲染：SQLite→0，PG→false）。
2. **`.dockerignore` 排除了 `app/tools`**：迁移/回填脚本进不了镜像，运维无法在容器内执行迁移。
   已放开该目录（`app/tests` 仍排除）。

### 6.4 发布打包（Docker）

- `deploy/Dockerfile` 与 `deploy/Dockerfile.single`：一并安装 `requirements-pg.txt`
  （`psycopg2-binary`，预编译 wheel，slim 镜像无需系统依赖）；
- `deploy/docker-compose.yml`：**默认改为 PostgreSQL 部署**（`db: postgres:16` +
  健康检查 + `pgdata` 卷 + `CTMS_DB_URL`），保留"改回 SQLite"的注释说明；
- 新增 `deploy/docker-compose.external-pg.yml`：连接**既有** PostgreSQL（如本项目的
  `192.168.31.27:5444`），连接串可由 `deploy/.env` 的 `CTMS_DB_URL` 注入；
- 单容器镜像导出流程不变：`scripts/export-docker.sh` / `export-docker.bat`
  （`docker build -f deploy/Dockerfile.single` → `docker save`），
  容器内执行迁移：`docker exec ctms python -m app.tools.migrate_sqlite_to_pg --sqlite /data/ctms.db --pg-url ...`。

**本次实测**（本机 Docker 29.8）：

```bash
docker build -t ctms:2.3.0 -f deploy/Dockerfile.single .      # 成功，镜像 211MB
docker save -o ctms-image-2.3.0.tar ctms:2.3.0               # 发布包
docker run -d --name ctms -p 8250:8000 \
  -e CTMS_DB_URL="postgresql+psycopg2://postgres:***@192.168.31.27:5444/ctms" ctms:2.3.0
# 实测：/api/health → {"status":"ok","db":true}（连的就是 PostgreSQL）
#       docker exec ctms python -c "import psycopg2" → 2.9.13
#       docker exec ctms python -m app.tools.migrate_sqlite_to_pg --help → 可用
#       /srv/web/dist 已含前端产物（单容器自带页面）
```

> 构建期若基础镜像拉取失败（例如镜像加速器返回 502），Docker 会自动回退到列表中的下一个
> mirror；`scripts/export-docker.*` 支持传入版本号（默认 `2.3.0`），产物为
> `ctms-image-<版本>.tar`。

## 7. 升级与回滚注意

1. **必须先跑迁移与回填**（顺序不可颠倒：回填的入库/出库单签约公司依赖仓库所属公司）：

   ```bash
   app\.venv\Scripts\python.exe -m app.tools.migrate_sqlite_to_pg --pg-url "<PG连接串>"
   set CTMS_DB_URL=<PG连接串>
   app\.venv\Scripts\python.exe -m app.tools.backfill_subject_v23 --dry-run   # 先预览
   app\.venv\Scripts\python.exe -m app.tools.backfill_subject_v23             # 再执行
   ```

2. **存量单据没有签约公司时无法编辑保存、也无法下推**（必填是两个动作的硬约束）——
   这正是回填脚本存在的原因；如业务上要按不同主体拆分，请在界面上逐单调整，
   回填脚本只填空值、不覆盖已填值。
3. **打印模板**：签约公司/调出单位/调入单位是**新增**的可配置表头字段。若之前已保存过
   某单据类型的打印模板，新增字段不会自动出现（模板语义是"以保存的清单为准"，
   见 `print_template_service._normalize_head_fields`）；到「系统管理 → 打印模板」勾选即可。
4. **回滚**：代码回滚到 V2.2 即可；数据库侧新增列可空、新表无（`warehouses.subject_code`、
   各单据 `subject_code/subject_name`、`stock_transfers.from/to_subject_*`），
   旧版本读取时会忽略，无需回退 DDL。若已切 PG，把 `CTMS_DB_URL` 指回 SQLite 文件即可。
