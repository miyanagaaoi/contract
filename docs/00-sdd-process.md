# 00. SDD（规格驱动开发）流程说明

> 本文说明"SDD 规范"在本项目中如何落地：不是一套文档模板，而是一条"**先把行为规格化，再开发、再按规格验证**"的开发主线。全项目文档均围绕规格展开。

## 1. 什么是 SDD

SDD（Specification-Driven Development，规格驱动开发）的核心思想：

1. **规格先行（Specification First）**：每个需求在动手写代码前，先被写成清晰、可验证的行为规格——业务规则 + 验收场景（Given-When-Then）。
2. **规格即契约**：开发按规格实现，测试按规格验收，规格是需求方与开发方唯一的"对错标准"。
3. **小步闭环**：每个功能走完 "规格 → 实现 → 场景验证" 才算完成，再进入下一个功能。
4. **规格随迭代演进**：需求变化先改规格，再改代码；规格文档永远反映系统"应该怎样"，而不是"曾经怎样"。

> 注：本项目不引入额外重量级流程，SDD 是对现有轻量敏捷做法的收紧——把"口头需求 / 模糊备注"替换为"可执行的验收场景"。

## 2. 本项目的规格化结构

项目采用三层规格：

| 层级 | 文档产物 | 回答的问题 | 对应文件 |
|---|---|---|---|
| 需求规格层 | 用户故事 + 业务规则（BR） | 系统**要做什么**、口径是什么 | `01-requirements.md` |
| 场景验收层 | Given-When-Then 验收场景（AC） | 怎样算**做对了**（可执行） | `01-requirements.md` 第 7 节 |
| 技术设计层 | 数据模型 / 接口 / 页面设计 | 系统**怎么做** | `02-system-design.md` |

## 3. 每个功能的标准生命周期（迭代内循环）

```
┌──────────────────────────────────────────────────────────┐
│  ① 编写/更新规格（需求条目 + 业务规则 + 验收场景）        │
│  ② 规格评审（开发自评 + 需求方确认口径，见 4.1）          │
│  ③ 按规格实现（数据模型 → 后端 → 前端）                  │
│  ④ 跑该功能的验收场景（手动冒烟 或 自动化断言）          │
│  ⑤ 场景全绿 → git commit（保存版本）→ 该功能 Done        │
│    否则回到 ③/①                                        │
└──────────────────────────────────────────────────────────┘
```

**完成的定义（Definition of Done）**：一个功能满足 **① 其全部验收场景通过 + ② 无遗留阻断问题 + ③ 已提交一次 Git 版本**（"每完成一个功能，保存一次 Git 版本"为强制纪律，见 `03-development-plan.md` §3.1）。

## 4. 落地要点

### 4.1 规格评审门禁（Spec Review Gate）

- 涉及**业务口径**的功能（金额、付款比例、质保、绑定）必须经过一次与需求方的规格确认；
- 评审以 `01-requirements.md` 的"业务规则 + 验收场景"为唯一评审对象，不评审代码；
- 评审通过后进入实现，避免"做出来再返工"。

### 4.2 验收场景的用法

- **原型阶段**：作为冒烟测试清单，每个功能做完逐条勾选，形成《原型验收报告》；
- **正式阶段**：可逐步把场景转成自动化测试（Python `pytest` + `behave`/`pytest-bdd`，或用 API 级断言脚本），实现"按规格回归"；
- **用户验收（UAT）**：直接拿场景清单让 3 类角色用户逐条演示确认，双方口径统一。

### 4.3 版本纪律（每功能一次 Git 提交）

- 一个功能（一组 AC 全绿）结束即 `git commit` 一次，commit 信息建议 `feat: [AC-xx] 功能名`；
- 规格文档变更与实现可同 commit（小步快走），但说明中注明；当日收工前必须至少 commit 一次；
- commit 记录同时充当进度证据与回溯点：出问题时可按"功能版本"回退，而不是面对一堆混改。

### 4.4 口径变更流程

需求方提出变化时，不直接改代码，先走：记录变更 → 更新对应 BR/AC → （涉及口径则）评审 → 再实现。变更记录统一登记在 `03-development-plan.md` 的"变更登记表"中。

## 5. 本项目文档与 SDD 的对应

| 交付物 | SDD 中的角色 |
|---|---|
| `01-requirements.md` | 需求规格（用户故事、BR、AC 清单）——开发与验收的依据 |
| `02-system-design.md` | 满足规格的技术方案（ER 图、状态机、页面、接口） |
| `03-development-plan.md` | 按功能/规格拆解的实施计划、里程碑、风险 |
| `04-tech-route.md` | 技术选型论证（含原型两套候选路线对比） |

## 6. 推荐配套工具（可选，正式阶段引入）

- 场景管理：`pytest-bdd` / `behave`（Python 生态）或轻量 Markdown 勾选清单（原型阶段足够）；
- 版本管理：Git（仓库内按 `docs/` + `app/` 分目录）；
- 用例与缺陷：原型阶段用简单清单即可，不引入单独平台。
