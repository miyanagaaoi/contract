# 04. 技术路线推介（选型论证）

> 结合已确认约束：纯内网单服务器、3~4 人、会代码可自维、先原型验证、后续可能演进。

## 1. 总体结论（TL;DR）

**推荐路线：Python 3.11 + FastAPI + SQLAlchemy + SQLite（原型）→ PostgreSQL（正式）；前端 Vue3 + Vite + Element Plus；部署 Linux + Docker Compose（Windows 内网无 Docker 则用备选原生部署）。**

理由一句话：单体架构 + 开发者友好的 Python/JS 组合，**原型 4 周内可交付验证，正式版不用推倒重来**，且完全满足纯内网、零外网依赖。

## 2. 候选方案对比

| 维度 | A. FastAPI + Vue3（推荐） | B. Django 全家桶 | C. 低代码私有化（如明道云/简道云私有版） | D. Excel/共享盘增强 |
|---|---|---|---|---|
| 原型速度 | 快（约 3.5~4.5 周含打磨） | 最快（Admin 自带 CRUD） | 最快（配表单即可） | 当天 |
| 符合"合同台账+标签+搜索+绑定+质保提醒" | ✅ 完全可控 | ✅ 完全可控 | ⚠️ 绑定/提醒/导出依赖平台能力，越界需求受限 | ❌ 标签筛选/绑定/历史都难以实现 |
| 纯内网部署 | ✅ 任意（无外网依赖） | ✅ | ⚠️ 私有化版通常有授权成本/离线包限制 | ✅ |
| 免登录直接可用（已确认不设账号/角色） | ✅ | ✅ | ✅ | ✅ |
| Excel 导出 | ✅ openpyxl | ✅ 生态成熟 | ✅ 平台自带 | ✅ 天然 |
| 数据模型可控/演进 | ✅ 强 | ✅ 强 | ❌ 受平台约束 | ❌ |
| 维护成本(自维) | 中低 | 低 | 平台订阅+培训 | 低但不可用 |
| 外包接手难度 | 低（主流栈） | 低 | 依赖平台厂商 | — |
| 长期扩展（付款明细/OCR/审批/移动） | ✅ 平滑 | ✅ 平滑 | ⚠️ 看平台版本 | ❌ |

**结论**：
- 若最终想"自己完全掌控 + 长期演进"，选 **A**（或 B，B 在快速 CRUD 上更强，A 在前端交互/结构上更清晰，二选一即可，本文默认 A）；
- 纯 Excel 直接否决（需求 5/6/7/8 无法满足）；
- 低代码私有化可作"完全没有开发人力"的备选，但你有自研能力，且纯内网 + 定制跟踪逻辑下并不省事，故不推荐为主路线。

## 3. 分层选型明细

### 3.1 后端语言与框架
| 候选 | 结论 |
|---|---|
| Python + FastAPI | ✅ 推荐：类型提示/Pydantic 校验、自动 OpenAPI 文档、异步可选、生态全 |
| Python + Django | ✅ 备选：Admin 零成本、ORM/迁移/Auth 内置；若追求最快 CRUD 可选它 |
| Java/Spring Boot | ❌ 对本规模过重，构建/维护成本高 |
| Go | ⚠️ 性能无关紧要，开发/招聘不如 Python 顺手 |
| Node.js(Nest/Express) | ⚠️ 可选项：若团队 JS 更强可选 NestJS；本文按前后端生态统一度推荐 Python 后端 |
| .NET | ❌ 除非公司现有 .NET 栈与运维习惯 |

### 3.2 前端
- **Vue 3 + Vite + Element Plus**（推荐）：后台管理场景组件最全（表格筛选、标签、日期、上传），中文文档好，构建后纯静态文件由 Nginx 托管，内网零依赖；
- 备选：React + Ant Design（同样可行，若团队更熟 React）；服务端模板（若走 Django 备选路线则配 Django Templates + Alpine.js 更省）。

### 3.3 数据库
- 原型：**SQLite**（单文件、零运维，3~4 人并发绰绰有余）；
- 正式：**PostgreSQL 16**（迁移由 SQLAlchemy 承担，成本约半天）；
- MySQL 亦可（若公司已有运维经验），PostgreSQL 默认优先。
- 不做 NoSQL：关系型数据（合同↔标签↔子合同↔历史）强一致更合适。

### 3.4 访问与账号（已确认：不做登录、不区分角色）
- **无账号、无登录、无角色**：系统监听内网地址，打开即用（决策见 `01` §2）；
- 取舍已文档化：修改不按人追溯 → 合同"经办人"字段 + 变更历史（时间/前后值）+ 每日备份兜底；
- 如需审计，演进方案见 `02-system-design.md` §12 第 7 条（改造成本小），因此**不为原型引入任何认证依赖**。

### 3.5 Excel 导出
- 后端 openpyxl 生成 .xlsx（大数据量可换 xlsxwriter/流式）；前端一个下载链接即可。

### 3.6 附件存储
- 本地磁盘目录 + 元数据入库；不上对象存储（内网无必要）；备份随附件目录策略。

## 4. 部署方案（服务器 OS 未定 → 给两套）

### 方案一：Linux + Docker Compose（推荐，若服务器可装 Docker）
```
docker-compose.yml:
  nginx      (80 端口, 静态 + /api 反代 + client_max_body_size 20m)
  app        (FastAPI, gunicorn/uvicorn, SQLite 卷或连 PG)
  db         (正式版 PostgreSQL, 数据卷)
  backup     (cron: 每日 DB dump + 附件增量到备份卷)
```
- 升级 = 替换镜像重启；迁移 = 拷数据卷。

### 方案二：Windows 内网（无 Docker / 公司规定 Windows）
- 后端：Python 3.11 安装为 Windows 服务（NSSM 托管 uvicorn）；
- 前端：构建后静态目录由 IIS 或 Nginx for Windows 托管；
- 数据库：SQLite 单文件或 Windows 版 PostgreSQL；
- 备份：计划任务每日执行备份脚本。
> 技术栈跨平台（Python/静态前端），OS 不影响选型，只影响部署脚本（两版部署手册在 P3 阶段编写）。

## 5. 安全与合规（内网仍要做）
- 部署边界：服务只监听内网（防火墙/网段隔离），不对外暴露；
- 上传类型白名单 + 大小限制 + 存储文件名随机化（防路径穿越）；
- SQL 注入防护：统一 ORM + 参数校验（无账号体系，故无越权/会话安全问题）；
- 附件预览仅同网段可访问（无外网天然收敛）；
- 行为留痕：合同级 CHANGE_LOG + 系统日志 + 每日数据备份（替代原"审计日志"职责）。

## 6. 演进路线（从原型到长期）
| 触发条件 | 演进动作 | 成本 |
|---|---|---|
| 原型验证通过 | 切 PostgreSQL、备份、部署手册、自动化测试 | 0.5~1 周 |
| 需要逐笔付款 | 新增 PAYMENT 表 + 视图替换累计字段 | 小 |
| 需要审批流 | 状态机加待办人字段 / 轻量流程引擎 | 中 |
| 需要邮件提醒 | 加每日定时扫描任务 | 小 |
| 附件 OCR/检索 | 内网 OCR 服务或评估方案 | 中 |
| 出现"谁改的"审计需求 | 引入账号与角色（见 02 §12 第 7 条），恢复操作人记录 | 小 |
| 公司强制上云 | 同架构平移到云主机/内网穿透，并建议补充账号体系 | 小 |

## 7. 推荐的最低技术栈（速查）
```
后端: Python 3.11 · FastAPI · SQLAlchemy 2.x · Pydantic v2 · openpyxl
（无认证依赖：无登录/无角色，见 §3.4）
前端: Vue 3 · Vite · Element Plus · Pinia · Vue Router · Axios
数据: SQLite(原型) → PostgreSQL 16(正式)
部署: Docker Compose / Nginx / systemd 或 NSSM(Windows)
版本: Git（Gitea 内网自建可选）
```

## 8. 备选路线补充：若选 Django
- 用 Django + Django Admin 直接获得 90% 后台能力（CRUD、搜索、导出），再以少量自定义页面覆盖：标签多选、框架绑定、看板预警；
- 注意：本方案同样**不启用登录/权限**——Django Admin 仅用于开发期调试（本地直连），正式入口为自定义页面（关闭认证中间件或使用单一内网口令），避免引入与决策相悖的账号体系；
- 周期可再压缩约 0.5~1 周；
- 代价：前端自由度/交互不如 Vue SPA；后续若要做复杂交互仍可加 API + Vue。

> 两条路线都可满足本文档全部规格，最终在 P2 决策会议定稿。若仍摇摆，**原型验证阶段就用推荐 A**，因其结构与最终正式版一致，决策风险最小。
