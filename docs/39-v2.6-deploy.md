# 39. V2.6 联动部署指南（核心包 / 同步扩展包 + 桥接通道）

> 前置文档：[10-docker-single.md](10-docker-single.md)（基础 Docker 打包）、
> [38-v2.6-invoice-sync-plan.md](38-v2.6-invoice-sync-plan.md)（V2.6 功能与通道设计）。
> 本文解决：**分包后到底怎么装、两条同步通道如何联动、旧版本如何平滑升级**。

## 1. 先理解"联动"的三种角色

| 角色 | 跑在哪 | 需要什么 | 负责什么 |
|---|---|---|---|
| **CTMS 容器** | 服务器（Docker） | 核心包 或 同步包（二选一） | 台账、列表、绑定、打印、入库 |
| **DSH 浏览器桥**（可选） | 办公机 | DSH 桌面版 + dsh-browser 扩展 | 直接读你**已登录**的税务平台页面 |
| **税务平台账号** | 浏览器会话 | 账号密码 + 手机验证码 | 提供发票数据（页面查询/下载发票包） |

关键点：**容器里没有浏览器也能用全部 V2.6 功能**——发票数据可以经两条通道进来：

- **通道 A 桥接**（推荐办公机部署）：办公机 DSH 读页面 → `POST /api/finance/invoices/import-rows` 入库；
- **通道 B 发票包**（最稳）：税务平台「下载→全部下载」→ CTMS「上传发票包」→ 解压挂 PDF；
- **通道 C Playwright**（仅同步包）：容器内自动登录抓取；生产环境受"无头浏览器无法人工过验证码"限制，
  需在会话保活 1 小时内发起，或把开发机会话文件复制进容器。

## 2. 场景一：只装核心包（推荐，90% 场景）

```bash
gunzip -c ctms-image-2.6.0-core.tar.gz | docker load     # 或 docker load -i *.tar.gz
docker run -d --name ctms -p 8080:8000 -v ctms_data:/data ctms:2.6.0
# 或: docker compose -f deploy/docker-compose.single.yml up -d
```

- 体积：**71MB（gzip）/ 212MB（镜像）**；
- 可用：发票列表/筛选/红字标记/绑定弹窗/收票进度/批量打印/发票包导入；
- 同步按钮点开时若无 Chromium，只会提示"同步不可用"，**不影响其它功能**。

日常操作闭环（无需任何浏览器自动化）：

1. 浏览器登录税务平台 → 查询类型「取得发票」→ 选日期 → 查询；
2. 若在办公机上：直接让 DSH 读页导入（通道 A）；
3. 点「下载 → 全部下载」拿发票包 → CTMS「上传发票包」挂 PDF（通道 B）；
4. 采购单「更多 → 登记进项发票」→ 勾选未确认票 → 确认绑定 → 收票进度自动累计。

## 3. 场景二：需要服务器端自动同步 → 同步包

```bash
gunzip -c ctms-image-2.6.0-sync.tar.gz | docker load
docker run -d --name ctms -p 8080:8000 -v ctms_data:/data \
  -e CTMS_TAX_SYNC_YX_USERNAME=xxx -e CTMS_TAX_SYNC_YX_PASSWORD=xxx \
  -e CTMS_TAX_SYNC_YX_TAX_NO=91149900MAECLDF33U \
  ctms:2.6.0-sync
# 或: docker compose -f deploy/docker-compose.sync.yml up -d
```

- 体积：**616MB（gzip）/ 1.5GB（镜像，含 Chromium）**；
- 首次同步：容器内会打开无头浏览器执行登录——若平台要求点字验证码，容器**无法人工操作**，
  此时先在有界面的开发机跑一次同步，生成 `app/data/tax_session/state_<主体码>.json`，
  再 `docker cp state_YX.json ctms:/app/app/data/tax_session/` 复用会话（1 小时保活内完成抓取）。

## 4. 两个包怎么"联动"

它们是**同一套系统的两个镜像变体**，不是两个服务：

- 共用**同一数据卷** `ctms_data`、同一容器名 `ctms`、同一端口映射；
- 切换 = `docker rm -f ctms` 后换镜像 `docker run`，**/data 里的库、附件、日志原样保留**；
- 也可以长期只用一个：办公机桥接为主就装核心包；要无人值守定时同步就装同步包。

```bash
# 例：核心包 → 同步包（数据不动）
docker rm -f ctms
docker run -d --name ctms -p 8080:8000 -v ctms_data:/data ctms:2.6.0-sync
```

## 4.1 分功能打包：Chromium 固定，只更新业务核心包（推荐长期用法）

### 分层结构

| 层 | 镜像 | 变化频率 | 体积（gzip） |
|---|---|---|---|
| 浏览器底座 | `ctms-browser:1` | **几乎不变**（仅 Playwright/Chromium 升级时） | ~575 MB |
| 业务核心 | `ctms:<版本>` | 每次业务更新 | ~71 MB |
| 同步镜像 | `ctms:<版本>-sync` | **服务器本地组装**，不传输 | 0（组装产物） |

底座 Dockerfile 见 [deploy/Dockerfile.browser](../deploy/Dockerfile.browser)（只装 Chromium+字体，无业务代码）；
组装 Dockerfile 见 [deploy/Dockerfile.sync-local](../deploy/Dockerfile.sync-local)（`FROM ctms-browser:1`，
从业务镜像 COPY `site-packages` / `app` / 前端 dist，**全程离线、秒级完成**）。

### 首次部署（同步版）

```bash
docker load -i ctms-browser-1.tar.gz          # 一次性
docker load -i ctms-image-2.6.0-core.tar.gz
docker build -t ctms:2.6.0-sync \
  --build-arg CORE=ctms:2.6.0 -f deploy/Dockerfile.sync-local .
docker run -d --name ctms -p 8080:8000 -v ctms_data:/data ctms:2.6.0-sync
```

### 以后每次业务更新（关键收益）

```bash
docker load -i ctms-image-2.6.1-core.tar.gz   # 只传 71MB，Chromium 层原地不动
docker build -t ctms:2.6.1-sync \
  --build-arg CORE=ctms:2.6.1 -f deploy/Dockerfile.sync-local   # 离线组装，几秒
docker rm -f ctms
docker run -d --name ctms -p 8080:8000 -v ctms_data:/data ctms:2.6.1-sync
```

> 对比：不拆分时每次要传 616MB；拆分后每次只传 **71MB**（约 1/9），且不再下载/重建 Chromium。
> 需要重建底座的唯一场景：Chromium/Playwright 大版本升级，或 Python 次版本变化（当前两镜像均 3.13）。

### 离线内网服务器能否 build？——可以（已实测）

`deploy/Dockerfile.sync-local` **不含任何 `RUN` 指令**，只有 `FROM` 本地镜像与 `COPY --from` 本地镜像，
因此不需要联网、不拉镜像、不装包。实测命令（网络完全禁用）：

```bash
docker build --network=none -t ctms:2.6.0-sync \
  --build-arg CORE=ctms:2.6.0 -f deploy/Dockerfile.sync-local .
# 实测结果：构建成功；容器内 chromium 156.0.8078.4 与业务依赖均正常
```

离线服务器首次准备（全部通过 `docker load` 导入，然后本地组装）：

```bash
docker load -i ctms-browser-1.tar.gz
docker load -i ctms-image-2.6.0-core.tar.gz
docker build --network=none -t ctms:2.6.0-sync --build-arg CORE=ctms:2.6.0 \
  -f deploy/Dockerfile.sync-local .
```

后续更新同理：只 load 新的 core 包，再 build 一次（几秒完成）。

> 若服务器连 Docker build 也不允许（如策略限制或没有构建工具），两条退路：
> ① 直接 load 全量同步包 `ctms-image-<版本>-sync.tar.gz`（616MB，功能相同）；
> ② 在有 Docker 的机器上组装好再 `docker save` 传过去（体积同全量包）。

> 若完全不想在服务器执行 build，仍可用全量同步包 `ctms-image-<版本>-sync.tar.gz`（616MB）直接 load，
> 二者功能完全相同——区别只在传输量。也可用私有 registry（`registry:2`）`push/pull`，
> Docker 只传输变化层，效果与本地组装一致。

## 5. 从 V2.5.x 平滑升级

```bash
docker stop ctms && docker rm ctms                 # 数据在卷里，安全
gunzip -c ctms-image-2.6.0-core.tar.gz | docker load
docker run -d --name ctms -p 8080:8000 -v ctms_data:/data ctms:2.6.0
docker logs -f ctms        # 启动时自动执行增量迁移（invoices 补列 + invoice_sync_logs 建表）
```

- 迁移幂等：`ensure_schema_upgrades()` 自动补 `sync_source/bind_status/is_red/...` 列与新表，重复执行安全；
- 升级后建议：登录 CTMS → 发票管理 → 确认"收票单位"筛选能筛出同步票（V2.6 已回填历史同步票的 `subject_code`）。

## 7. 常见问题

**Q1：只装核心包，能绑定发票到采购单吗？**
能。绑定、进度、红字标记、打印全部在核心包；只缺"服务器自动抓取"。

**Q2：桥接通道要不要在服务器装 dsh？**
不要。桥接跑在**办公机**（DSH 桌面版 + 浏览器扩展），它通过 HTTP 调容器里的
`/api/finance/invoices/import-rows`（需登录态 token）。

**Q3：同步包里的 Chromium 会不会占太多内存？**
仅在同步任务运行时启动浏览器（约 300–500MB 峰值），任务结束即关闭。

**Q4：数据备份怎么办？**
沿用既有方案：`/data` 卷内的 `ctms.db` + `uploads/`；详见 `15-backup-drill.md`。
